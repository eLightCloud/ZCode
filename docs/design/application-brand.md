# Optional application branding

An application assembly may wrap the public Root in ApplicationBrandProvider. The static ApplicationBrand projection supplies name, attribution, Mark and Wordmark components. It owns no credentials, tenant, theme, execution or native provider state. The default unwrapped Root retains native branding. ApplicationShell is an optional trusted assembly module from ZCODE_APPLICATION_SHELL_MODULE. It wraps each complete renderer tree before Intl, startup, account and share rendering; without it the shell is React Fragment. localizedNames optionally selects display names by locale. Product-level messages substitute standalone native product references; Agent, MCP, CDN, provider, official plugin identity, third-party entitlement campaigns and protocol names retain their source identity. Mixed messages substitute app references while preserving actual runtime labels.

HTML entry points may use applicationBrandPlugin with an absolute trusted ZCODE_APPLICATION_BRAND_MANIFEST. Schema 1 supplies applicationName and adjacent source.svg / assets. The plugin replaces the page title and startup mark, serves or emits a finite set of favicon / mobile assets, and rejects missing configuration. Request parameters cannot choose manifests or filesystem paths.

React startup loading, including database preparation and onboarding badges, consumes the same provider Mark as the rest of the application. The HTML startup mark and React loading mark must agree during handoff. Branded marks retain their own SVG geometry and the existing badge size, color, optional breathing animation and accessible loading status; no-configuration rendering keeps the native mark. Startup admission and readiness events are unchanged.

The new-task draft greeting also consumes the configured Mark. Render it in a responsive square above the greeting, retaining its own SVG proportions and semantic muted foreground in both themes. This decoration is hidden from accessibility and pointer input. Native Z-specific artwork and fading apply only when no application brand is configured.

Desktop identity accepts optional application name, ID, executable and package values, with native Preview separation. Icons and installer resources use an absolute ZCODE_APPLICATION_ICON_DIR supplied by assembly. Packaged runtime names use Electron package identity; development runtime names retain the existing explicit configuration boundary. Branding never changes the protocol scheme or native storage keys.

Validate no-configuration native behavior, branded titles and symbols, retained provider names, malformed manifest rejection, Preview identity separation, public-asset serving and emitted bundle assets. Test both UI themes and mobile widths. Verify shell ordering before Intl, independent resource windows, shared Web/share branding, system folder-menu labels and Computer Use status panels. Verified Helper display names must still match the actual permission identity. Branding asset configuration is not evidence of signing or successful installation.

Trusted bootstrap assembly may supply `AgentRuntimeConfig.productName` (or its existing `ZCODE_APPLICATION_NAME` startup identity) for built-in main and subagent identity text. Core consumes a bounded plain display name, defaults to native ZCode, and inherits it into child runtimes. It changes no executable, protocol, agent ID, permission, persisted state or caller-authored prompt/profile. Invalid control characters are rejected before context construction. Source and copyright attribution remains in the separate legal area.

The Server CLI accepts the same trusted `ZCODE_APPLICATION_NAME` at its process entry. Human-readable lifecycle headings, update results and uninstall prompts use that bounded display name; without it they retain ZCode. JSON product identifiers, protocol fields, manifests, service ownership and runtime diagnostic details keep their original technical identity. The CLI passes the display name through its existing output dependency rather than rewriting arbitrary output or persisted data.

Branded Desktop packaging sets the package description from the same resolved product display name. Native unconfigured package descriptions, author/source metadata, protocol keys and legal notices remain unchanged. A package description is a product-facing installer/file-information field, not a substitute for source attribution.
